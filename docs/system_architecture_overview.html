Local-first runtime architecture

AI Agent macOS system flow from SwiftUI input to Gemini reasoning to local tool execution

This app is a two-process system. The macOS UI runs in SwiftUI and talks over authenticated NDJSON JSON-RPC on a Unix domain socket to a Python backend. The backend owns model orchestration, tool validation, tool execution, session persistence, semantic memory, notes, and final response formatting. The frontend owns process launch, transport, state, streaming UX, and message rendering.

Startup Flow

1. Swift app boots

AIAgentUIApp creates AppState.shared and window/panel surfaces.

2. Backend process launches

BackendLauncher resolves Python env, validates runtime requirements, and starts python -m agent_host.main --server.

3. Socket becomes available

The backend starts the IPC server and emits readiness logs including socket context and auth token.

4. Frontend connects

SocketManager opens the Unix socket, IPCClient authenticates, and AppState begins session/bootstrap refresh.

Swift process owns UX and connection recovery Python process owns request orchestration Transport is local-only Auth token rotates across reconnects

End-to-End Prompt Lifecycle

Frontend path

  1. User types into MainPanelView.
  2. AppState.sendPrompt() validates connection, active session, selected model, memory mode, execution mode, browse profile, and deep-think compatibility.
  3. IPCClient.send(...) builds a PromptRequest JSON-RPC envelope and sends it via SocketManager.
  4. UI enters thinking/streaming state and waits for status, stream, tool, and result messages.

Backend path

  1. main.py::handle_prompt() parses request params and validates request shape.
  2. Backend resolves session, memory mode, execution mode, verbosity, presentation style, deep-think flag, browse profile, and input paths.
  3. MemoryManager.prepare_prompt_context() augments the user prompt with recent turns, semantic hits, summaries, and notes.
  4. build_system_prompt() + inject_model_identity() produce the final system instruction.
  5. GeminiClient.send_prompt_with_tools() calls Gemini with runtime tool declarations.

Critical orchestration idea

The backend does not just ask the model for plain text. It sends the model a full tool belt, validates any returned function call against local JSON schemas, and then either executes the tool locally or continues the reasoning loop until it has a final answer or a plan/result to return.

Tool Execution Flow

1. Model proposes a tool

ToolCallParser extracts the first function call from the Gemini response.

2. Local schema validation

SchemaValidator validates tool arguments against the JSON file under schemas/.

3. Execution gateway

ToolExecutor.execute() routes the validated call to the correct local handler with path normalization, policy checks, and timeout control.

4. Result returns to model

The backend wraps the tool result as a Gemini function_response and continues the chain.

General tools

Search, metadata, text reading, extraction, file operations, automation, and browsing all go through agent_host/tools/executor.py.

Special-case tool families

read_screen is delegated back to the frontend through IPC because the backend cannot directly inspect the user’s current screen. Notes/image note flows are dispatched through tools/registry.py.

Approval gates

Destructive actions are intercepted. The backend emits awaiting_approval, the UI shows the confirmation state, and execution resumes only after tool.confirm.

Sessions, Memory, and Notes

Session model

Persistent transcript All chat turns are appended to the session store so session switching and history paging work regardless of semantic memory mode.
Memory modes on, off, ephemeral change retrieval and semantic persistence behavior, not whether the chat transcript exists.
History paging The UI uses session.history_page to keep only a bounded live message window loaded.

Semantic memory

Preparation MemoryManager.prepare_prompt_context() pulls recent turns, summaries, semantic hits, and notes into the prompt context.
Persistence record_interaction() appends user/assistant messages and optionally updates semantic memory.
Embeddings EmbeddingService is late-bound to the Gemini client and used for retrieval/ranking.

Notes are first-class data

Notes are not just formatted assistant output. They have dedicated CRUD IPC methods, version history, note images, and special tool flows. Teacher mode can automatically capture study notes through the note tool path.

Gemini / Model Flow

1. Live catalog load

The backend exposes models.list, backed by GeminiClient.list_text_models().

2. UI selection

The Swift app fetches the live model catalog and stores only a selected model ID, not a hardcoded enum.

3. Request-time identity

inject_model_identity() prepends the actual model ID into the system prompt so the assistant can answer truthfully about its current model.

4. Capability checks

Deep-think and image model selection are derived from live metadata / model IDs, not a frozen UI model list.

Text generation

GeminiClient.send_prompt_with_tools() and send_continuation() call client.models.generate_content() with tools, system instruction, and optional thinking config.

Continuation loop

The backend preserves Gemini Content history and feeds back function_response parts, so the model can chain tools instead of hallucinating a final answer too early.

Image generation

Image-capable models are discovered from the live model catalog. The backend ranks available image models instead of pinning retired model IDs.

UI Rendering and Streaming Flow

Inbound messages from backend

Status thinking, planning, calling tool, awaiting approval, executing plan, streaming, complete.
Stream chunks delta text plus done flag.
Tool lifecycle pending, executing, success, failed.
Final result formatted assistant message and optional tool summary payload.

UI state ownership

IPCClient parses transport-level messages and exposes typed callbacks.
AppState owns message rows, streaming text, request lifecycle, session paging, selected model, permissions state, and settings.
MainPanelView renders the live chat window.
ResponseBubble renders assistant/user messages, streaming state, tool status in the compact response header, and browse warnings.

Current chat-window architecture

The newest region stays live while older messages load on demand. The UI uses a bounded live window and history paging to avoid rendering the full transcript at once. This keeps long sessions responsive while preserving the current conversation tail in real time.

Security and Operational Guardrails

Schema validation

Every tool call must match the local JSON schema before execution.

Path normalization

ToolExecutor clamps and validates user paths against allowed roots and safety rules.

Approval gates

Destructive operations pause for explicit user confirmation.

Timeouts / retries

Model calls, DB operations, and tool execution are wrapped with bounded timeouts and request-in-flight checks.

Browse controls

browse_web.py layers SSRF defenses, host blocking, prompt-injection checks, robots/compliance policy, and profile-based browsing rules.

Memory privacy

Semantic memory flows run through guardrails, sanitization, quarantine checks, and encrypted local storage.

Transport safety

Local socket only, authenticated handshake, version/feature negotiation, structured errors, and reconnect handling.
